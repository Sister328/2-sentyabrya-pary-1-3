# Документация и DevOps — проект «Перекуп»

**Роль:** технический писатель и DevOps (документация и организация разработки).  
**Цель документа:** описать архитектуру, структуру репозитория, командную работу, документацию, тестирование, выпуск и сопровождение проекта.

> Игра описана на этапе концепции. Предлагаемые решения нужно сверить с реальным кодом команды перед сдачей.

## 1. Описание продукта и бизнес-логика

«Перекуп» — экономическая игра о покупке подержанных автомобилей, ремонте и перепродаже с целью получения прибыли.

### Основные сценарии

| Код | Сценарий | Ожидаемый результат |
|---|---|---|
| СЦ-01 | Открыть карту | Игрок видит доступные локации |
| СЦ-02 | Найти машину | Игрок просматривает объявления и характеристики |
| СЦ-03 | Торговаться | Реплики влияют на цену, доверие или вероятность сделки |
| СЦ-04 | Купить машину | Деньги списываются, автомобиль становится собственностью игрока |
| СЦ-05 | Оформить кредит | Банк создаёт запись о долге |
| СЦ-06 | Купить запчасти | Проверяется баланс, детали добавляются в инвентарь |
| СЦ-07 | Отремонтировать машину | Меняется состояние автомобиля, списываются деньги/детали и игровое время |
| СЦ-08 | Продать машину | Покупатель-бот предлагает цену, игрок принимает или отклоняет её |
| СЦ-09 | Сохранить игру | Состояние можно восстановить при следующем запуске |

### Бизнес-правила
1. Баланс не может стать отрицательным из-за обычной покупки; кредит оформляется отдельно.
2. Покупка запрещена, если средств недостаточно.
3. У автомобиля есть состояние отдельных узлов: например, двигателя, кузова и ходовой части.
4. Самостоятельный ремонт дешевле, но может завершиться неудачей.
5. Ремонт на СТО стоит дороже и занимает игровое время, но должен быть надёжнее.
6. Переговоры ограничены доступными вариантами реплик и допустимым диапазоном цены.
7. Продать можно только принадлежащий игроку автомобиль.
8. За одно принятое предложение оплата начисляется только один раз.
9. Сохранение должно согласованно хранить деньги, машины, запчасти, объявления и долги.

## 2. Архитектура: модульный монолит

Для учебного проекта предлагается **модульный монолит**: одна программа с модулями, каждый из которых отвечает за свою задачу.

**Почему это подходит:** команда небольшая, система пока не требует независимого масштабирования сервисов, а запуск и отладка должны быть простыми.

**Преимущества:** единый запуск, проще тестирование, меньше инфраструктуры.  
**Недостатки:** приложение выпускается целиком; модули тесно связаны, если не соблюдать границы ответственности.

### Слои приложения
1. **Пользовательский интерфейс** — карта, объявления, чат, гараж, магазин, банк и СТО.
2. **Управление игровыми сценариями** — переходы между экранами и выполнение действий.
3. **Ядро предметной области** — игрок, автомобиль, запчасть, объявление, кредит.
4. **Сервисы** — торговля, ремонт, банк и диалоги.
5. **Хранение данных** — сохранения, база данных и журналы ошибок.

Интерфейс не должен напрямую менять внутренние поля объектов. Вместо этого он вызывает публичные методы, например `player.buy_car(car)` или `repair_service.repair(car, parts)`.

## 4. GitHub и командная работа

### Ветки
- `main` — проверенная версия для сдачи.
- `develop` — общая интеграционная ветка.
- `feature/<номер>-<название>` — новая функция.
- `fix/<номер>-<название>` — исправление ошибки.
- `docs/<номер>-<название>` — изменение документации.

### Процесс внесения изменений
1. Создать задачу и описать критерии готовности.
2. Создать отдельную ветку.
3. Реализовать функцию и при необходимости тесты.
4. Обновить README и связанные документы.
5. Создать Pull Request.
6. Получить проверку другого участника команды.
7. Слить изменения после успешной проверки.
8. Перед сдачей зафиксировать версию проекта.

### Примеры сообщений коммитов
- `feat: добавить экран объявлений`
- `fix: запретить повторную оплату продажи`
- `test: проверить неудачный ремонт`
- `docs: описать формат сохранения`

Не хранить в Git пароли, токены, ключи и реальные персональные данные. Добавить `.gitignore` для виртуального окружения, кэша, логов и временных сохранений.

- Для каждой версии фиксируются изменения и известные дефекты.

## 6. UML и модель данных

Исходник схемы хранится в `architecture.puml`, а картинка — в `architecture_diagram.svg`.

| Сущность | Примеры атрибутов |
|---|---|
| Игрок | идентификатор, баланс, наличие гаража, инвентарь |
| Автомобиль | идентификатор, марка, модель, год, пробег, состояние, владелец |
| Запчасть | идентификатор, название, цена, совместимость |
| Объявление | идентификатор, автомобиль, продавец, цена, статус |
| Кредит | идентификатор, заёмщик, сумма, остаток долга, ставка |
| Сеанс диалога | идентификатор, собеседник, этап, результат |
| Запись ремонта | автомобиль, тип ремонта, стоимость, результат, игровое время |

Для первого прототипа можно использовать JSON. Если данных станет больше, можно перейти на SQLite.

Примеры связей:
- **1:1** — игрок и профиль игрока, если профиль хранится отдельно.
- **1:N** — один игрок владеет несколькими автомобилями.
- **1:N** — один автомобиль имеет много записей истории ремонта.
- **M:N** — разные модели автомобилей используют разные виды запчастей; связь можно хранить в таблице совместимости.

## 7. Безопасность и целостность данных

- Проверять типы и диапазоны цен, баланса, состояния деталей и вероятности ремонта.
- Все изменения выполнять через публичные методы и сервисы, а не напрямую из интерфейса.
- При загрузке сохранения проверять структуру, версию и допустимые значения.
- Сохранять данные через временный файл с последующей заменой основного, чтобы снизить риск повреждения.
- Не записывать секреты и чувствительные данные в логи.
- Если появятся учётные записи, пароли хранить только в виде стойких хешей; сетевое соединение защищать HTTPS.
- Для веб-версии учитывать XSS, CSRF, инъекции, слабую аутентификацию и разграничение доступа.

## 8. Правовые требования

- **152-ФЗ «О персональных данных»** — применим при обработке персональных данных в сфере действия российского законодательства. Нужно определить цель и правовое основание обработки, минимизировать данные, ограничить срок хранения и обеспечить защиту.
- **149-ФЗ «Об информации, информационных технологиях и о защите информации»** — учитывать применимые требования к защите информации и её законному использованию.
- **GDPR** — учитывать, если обработка подпадает под территориальную сферу действия регламента, например в определённых случаях при работе с людьми в ЕС.
- **Согласие и политика конфиденциальности** — подготавливаются с учётом реальных целей и правового основания обработки; один чекбокс не является универсальным решением.

Для учебного прототипа лучше использовать только вымышленных персонажей и не собирать реальные ФИО, телефоны, адреса или платёжные данные. Перед коммерческим запуском нужна отдельная правовая проверка. Этот раздел не является юридическим заключением.

## 9. Тестирование и контроль качества

Предлагаемые инструменты для Python — `pytest` для автотестов и `ruff` для проверки кода. Выбор нужно согласовать с фактическим стеком команды.

Минимальные проверки:
- покупка при достаточном и недостаточном балансе;
- отклонение некорректной цены;
- успешный и неуспешный ремонт;
- правильное списание средств и игрового времени;
- оформление и погашение кредита;
- запрет продажи чужого автомобиля;
- защита от повторного начисления оплаты;
- сохранение и восстановление денег, автомобилей и долгов;
- корректная обработка повреждённого файла сохранения.

### Шаблон отчёта об ошибке
```text
Номер: BUG-001
Заголовок: Повторное зачисление оплаты за автомобиль
Шаги: принять одно предложение о покупке дважды
Ожидаемый результат: оплата начисляется один раз
Фактический результат: описать наблюдаемое поведение
Серьёзность: блокирующая / критическая / высокая / низкая
Статус: открыта / исправляется / исправлена / проверяется / закрыта
```

## 10. Сборка, выпуск и развёртывание

Для локального запуска:
1. Получить исходный код из GitHub.
2. Установить совместимую версию Python, если проект написан на Python.
3. Создать виртуальное окружение.
4. Установить зависимости из `requirements.txt`.
5. Запустить приложение по инструкции README.
6. Проверить основные сценарии по чек-листу.

В будущем можно добавить GitHub Actions для запуска тестов, проверки стиля кода и сборки. Пока файл автоматизации не добавлен и не проверен, нельзя считать CI/CD уже работающим.

## 11. Сохранения, резервные копии и мониторинг

- Сохранять состояние после важных операций: покупки, ремонта, кредита и продажи.
- Перед изменением формата сохранения создавать резервную копию.
- Добавить номер версии формата сохранения.
- При ошибке загрузки показывать понятное сообщение и предлагать резервную копию.
- Для локальной версии достаточно журнала ошибок и тестов; сетевой версии дополнительно нужны метрики доступности и ошибок.
- Не записывать в логи приватные сообщения или идентифицирующие данные без необходимости.
